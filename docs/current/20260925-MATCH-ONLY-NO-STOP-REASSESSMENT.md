# No-stop route: prefer match elimination over layout changes (2026-09-25)

This follow-up revises the recommendation in [the first type-indexed probe](./20260925-TYPE-INDEXED-NO-STOP-PROBE.md). Its representation-changing compiler patch remains useful evidence, but is **not** the version to productionalize first. A [smaller isolated candidate](../../experiments/affine_xf/no_stop_match_only_compiler.patch) leaves datatype layout and generic ABI unchanged and removes only match branches whose constructor requires a live value of a zero-constructor datatype. It handles a now-redundant default arm as well. No public library or sibling Bend checkout was changed for this follow-up.

The same generic `Flow<K,S>` source fold uses `K=Empty` for a total reducer and `K=Unit` for a reducer that may stop. The source-facing driver still returns only `S`. In a 14-run randomized native sample on this desktop (microseconds, source construction outside the timed region, one thread), the result was:

| Source | Stock direct | Stock indexed total | Match-only direct | Match-only indexed total |
| --- | ---: | ---: | ---: | ---: |
| Array, 2^18 leaves | 1946.5 | 2032 | 1963 | 1997.5 |
| Branching tree, 2^16 leaves | 147 | 166.5 | 146 | 146 |

The earlier layout-changing candidate measured 1943.5/1964.5 µs for Array direct/total and 148/147.5 µs for tree direct/total in that same sample. The match-only candidate is effectively at direct speed on the tree and close on Array, without changing any value representation. Its generated C still contains a tag and a condition around a statically `Ready` inspection result; Clang appears to remove their cost in the native program. This requires an optimized-machine-code check and a JavaScript performance check before claiming the condition is free on every target. Combined fixture C size was 171,468 bytes stock and 170,640 bytes match-only, versus 168,755 with layout pruning. The smaller code-size saving is not a reason to take the larger ABI risk now.

The match-only candidate passes the full 40/40 repository gate, including JS/native semantics, code-shape, source/mapper count, source rejection, and bounded laws. Focused cases cover a separate zero-constructor datatype, explicit and default match arms, an ordinary generic function boundary, an owned Array accumulator, initial stopping, and nested stop propagation. Process-level C generation medians over ten randomized invocations were 210.0 ms stock versus 213.7 ms match-only for the probe, and 283.5 versus 292.6 ms for `mapcat_public`. Bun startup is included; the possible compile-time cost needs profiling or a larger fixture before it is accepted.

## Recommendation

Take the **type-indexed stopping** route, but use conservative match elimination as the first compiler feature. It makes the proof explicit in library types, scales to new transducers without recognizing their names in the compiler, and keeps one source protocol. Do not merge either experimental patch as-is. The match-only patch is intentionally small, but its per-match constructor inspection and default-arm handling need a general correctness audit and likely caching.

The smallest public-library vertical slice should add a stop permit as an associated erased type in `Reducer<A,R>`: `Control<K,S>` has `Continue{S}` and `Stop{permit:K,state:S}`. A total reducer chooses `K=Empty`; a stopping reducer chooses `K=Unit`. `start` and `step` return `Control<Permit(reducer),State(reducer)>`. `map`, `filter`, `keep`, and `mapcat` inherit the downstream permit; `take` and zero-width partitioning can stop and use `Unit`. Keeping the permit *inside the reducer recipe* should leave the existing `Xf` provider composition shape intact. It must be checked in Bend rather than assumed. Unknown or custom reducers should use the stopping path unless their declared recipe proves totality.

The source `Drive` type then takes the permit as an erased parameter and receives `inspect: S -> Checked<K,S>`, while continuing to return `S`. The `transduce` boundary selects `K` from its final reducer recipe. This should not alter call sites such as `transduce(xf, sum_rf(), 0, xs)` or `into(dest, xf, xs)`. The first slice should implement `sum`, `map`, `filter`, `take`, Array, and one independent source. Build it under stock Bend for semantics and under the match-only candidate for speed. If the actual public call does not reach the direct-code performance range, stop and diagnose that gap before rewriting the rest of the library.

If that slice succeeds, harden the compiler rule against imported and instantiated datatypes; multi-scrutinee matches; default arms; affine fields; boxed and recursive values; arrays of indexed values; generic function boundaries; zero-arm types; and native, JS, and GPU behavior where available. Differentially compare stock and candidate outputs across these shapes. Keep the rule conservative when the field's emptiness cannot be proved. Profile the per-match work and cache instantiated constructor reachability if it is a real compile-time cost. No representation or ABI change is needed unless the public benchmarks show that match-only elimination fails.

Finally, propagate the permit through every reducer constructor and source adapter, preserving initial stop, nested `mapcat` stop (Clojure's preserving-reduced behavior), one-time completion, and affine ownership. Benchmark actual public total and stopping pipelines on Array, List, Range, and custom sources against equivalent direct Bend. Treat direct-speed parity for large total folds, no material stopping regression, and no significant compile-time growth as the release gates. If the narrower compiler rule cannot meet those gates, consider separate total source drivers before reviving the broader layout rewrite.
